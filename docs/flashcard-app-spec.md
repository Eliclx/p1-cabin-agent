# 知识卡片系统 — 需求规格 v2

> 核心理念：Agent 驱动的自适应复习系统。一张知识卡 → 四种题型自动生成 → Agent 评估 → 动态调整。

---

## 一、和普通卡片 App 的本质区别

| 普通卡片 (Anki/Quizlet) | 本系统 |
|------------------------|--------|
| 翻卡片，自己判断懂不懂 | Agent 出题 + 评估你是否真懂 |
| 固定 Q&A，永远不变 | 同一知识点自动生成四种题型 |
| 只有问答题 | 选择题 / 填空题 / 问答题 / 场景题 |
| 独立卡片，无关联 | 知识图谱关联，薄弱点自动聚类 |
| 只能刷已有卡 | Agent 按需生成新卡 |
| 被动看 | 主动对话式学习 |
| 题目固定不变 | 同一张卡每次出题不一样（agent 变换） |

---

## 二、四种题型设计

### 核心理念：一张卡片 → 四种题型

每张知识卡片有一个基础 Q&A。Agent 可以从这个基础内容**自动生成**四种不同题型的题目。

```
基础卡片: "三层推理漏斗的设计"
  ├─ 选择题: "FastRules 的延迟大约是？A.0ms B.100ms C.1s D.5s"
  ├─ 填空题: "端侧 3B 的 confidence 阈值是 ____，低于此值自动 fallback 到____"
  ├─ 问答题: "三层推理漏斗的设计和各自职责？"
  └─ 场景题: "用户说'帮我找最近的加油站'，FastRules 没命中短路，端侧返回 confidence=0.6，系统会怎么处理？"
```

**四种题型的认知层级：**

| 题型 | 认知层级 | 考察什么 | 适合阶段 |
|------|---------|---------|---------|
| 选择题 | 识别 (Recognize) | 能不能从选项中认出正确答案 | 初学、快速过 |
| 填空题 | 回忆 (Recall) | 能不能精确回忆关键术语/数据 | 巩固阶段 |
| 问答题 | 理解 (Understand) | 能不能用自己的话说清楚 | 准备面试 |
| 场景题 | 应用 (Apply) | 能不能把知识用到实际场景中 | 深度掌握 |

**面试考察规律**：选择题和填空题不会出现在面试中，但答不好说明基础不牢。面试考的是问答题和场景题。所以**四种题配合使用**：先刷选择+填空打基础，再过渡到问答+场景练表达。

---

### 题型 1：选择题

**特点**：快速、低门槛、碎片时间刷

**数据结构**：
```json
{
  "type": "choice",
  "card_id": "p1-arch-003",
  "question": "三层推理漏斗中，FastRules 的延迟大约是？",
  "options": [
    {"id": "A", "text": "0ms", "correct": true},
    {"id": "B", "text": "~100ms"},
    {"id": "C", "text": "~1s"},
    {"id": "D", "text": "~5s"}
  ],
  "explanation": "FastRules 是纯规则匹配，0ms 延迟，~40% 请求在此层短路。端侧 ~1s，云端 ~5s。",
  "distractor_source": "端侧和云端的延迟数据作为干扰项"
}
```

**Agent 的作用**：
1. **生成干扰项**：从关联卡片中提取相似但错误的选项（不是随便编的，是"看起来对但其实不对"的选项）
2. **变换问法**：同一知识点每次问的角度不同
   - 第 1 次：问延迟数据
   - 第 2 次：问覆盖率
   - 第 3 次：问哪层用 LLM
3. **根据错误调整**：选错了 → agent 分析为什么选错 → 下次出针对该误解的题

**交互**：
```
┌─────────────────────────────┐
│  选择题        3/15          │
│                              │
│  三层推理漏斗中，FastRules    │
│  的延迟大约是？               │
│                              │
│  ┌─────────────────────────┐│
│  │ A. 0ms                  ││
│  └─────────────────────────┘│
│  ┌─────────────────────────┐│
│  │ B. ~100ms               ││
│  └─────────────────────────┘│
│  ┌─────────────────────────┐│
│  │ C. ~1s                  ││
│  └─────────────────────────┘│
│  ┌─────────────────────────┐│
│  │ D. ~5s                  ││
│  └─────────────────────────┘│
└─────────────────────────────┘

选中后：
┌─────────────────────────────┐
│  ✅ 正确！                   │
│                              │
│  A. 0ms ← 你的选择           │
│                              │
│  💡 FastRules 是纯规则匹配，  │
│  0ms 延迟，~40% 请求在此层   │
│  短路。端侧 ~1s，云端 ~5s。  │
│                              │
│  [下一题]                    │
└─────────────────────────────┘
```

**出题规则**：
- 4 个选项，1 正确 3 干扰
- 干扰项必须**来自同一知识域的真实数据**（不能编造）
- 每张卡每次出题选项顺序随机
- 连续 2 次选对 → 这张卡的选择题暂时不出了

### 题型 2：填空题

**特点**：精确回忆，考关键术语/数据/流程

**数据结构**：
```json
{
  "type": "fill_blank",
  "card_id": "p1-arch-003",
  "template": "三层推理漏斗：L0 ___(~___% 覆盖) → L1 ___(~___s) → L2 ___(~___s)",
  "blanks": [
    {"id": 1, "answer": "FastRules", "alternatives": ["fast_rules", "前置规则"]},
    {"id": 2, "answer": "40", "alternatives": ["~40", "百分之四十"]},
    {"id": 3, "answer": "1", "alternatives": ["~1", "一"]},
    {"id": 4, "answer": "5", "alternatives": ["~5", "五"]}
  ],
  "explanation": "L0 FastRules 0ms/~40% → L1 端侧3B ~1s/~60% → L2 云端LLM ~5s/100%"
}
```

**Agent 的作用**：
1. **选择挖空位置**：同一段内容，每次挖不同的空（不总是挖同一个术语）
2. **模糊匹配**：用户填 "FastRules" 或 "fast rules" 或 "前置规则" 都算对
3. **提示生成**：填不出来时，agent 给渐进式提示而非直接给答案

**交互**：
```
┌─────────────────────────────┐
│  填空题        3/15          │
│                              │
│  三层推理漏斗：              │
│  L0 [________](~[___]% 覆盖)│
│  → L1 [________](~[___]s)   │
│  → L2 [________](~[___]s)   │
│                              │
│  [提交]        [提示]        │
└─────────────────────────────┘

点击提示后（渐进式）：
┌─────────────────────────────┐
│  💡 提示 (1/3)               │
│  L0 层是纯规则匹配，名字含    │
│  "Fast" 和 "Rules"...       │
│                              │
│  [继续填] [看答案]           │
└─────────────────────────────┘
```

**出题规则**：
- 支持**部分挖空**：不必全部填对，按填对比例给分
- alternatives 列表做模糊匹配
- 3 次提示后自动显示答案
- 填空题答不好 → 自动推送对应的选择题（降级）

### 题型 3：问答题

**特点**：开放式，考表达能力，最接近面试

**数据结构**：
```json
{
  "type": "essay",
  "card_id": "p1-arch-003",
  "question": "三层推理漏斗的设计和各自职责？",
  "reference_answer": [
    "L0 FastRules (0ms, ~40%)：30+ 条确定性规则短路",
    "L1 端侧 3B (~1s, ~60%)：Qwen2.5-3B-AWQ，conf < 0.85 自动 fallback",
    "L2 云端 LLM (~5s, 100%)：最终兜底，动态 Schema + few-shot"
  ],
  "eval_keywords": ["FastRules", "0ms", "端侧", "3B", "云端", "LLM", "兜底", "40%"],
  "followup": {
    "q": "为什么不直接全走云端？",
    "a": "车载场景低延迟要求，~40% 请求 0ms 响应"
  },
  "variation_questions": [
    "如果端侧模型挂了，系统怎么处理？",
    "FastRules 的 OOS 为什么不直接拒绝？",
    "三层漏斗的 fallback 机制是怎样的？"
  ]
}
```

**Agent 的作用**（这是 agent 价值最大的题型）：
1. **评估回答质量**：不是简单关键词匹配，agent 理解语义判断是否真懂
2. **追问**：回答不完整时追问细节，模拟面试官
3. **变换问法**：每次问法不同，防止背答案
4. **识别"背诵 vs 理解"**：回答过于模板化 → 追问一个变形题验证

**交互**：
```
┌─────────────────────────────┐
│  问答题        3/15          │
│                              │
│  三层推理漏斗的设计和各自     │
│  职责？                      │
│                              │
│  ┌─────────────────────────┐│
│  │ [输入你的回答...]        ││
│  │                         ││
│  │                         ││
│  └─────────────────────────┘│
│                              │
│  [提交]     [跳过看答案]     │
└─────────────────────────────┘

提交后 Agent 评估：
┌─────────────────────────────┐
│  📊 Agent 评估               │
│                              │
│  得分: 3.5/5                 │
│                              │
│  ✅ 提到了 FastRules、端侧、  │
│     云端三层                  │
│  ✅ 给出了延迟数据            │
│  ❌ 漏了 FastRules 覆盖率    │
│  ❌ 没提端侧的 conf 阈值机制  │
│                              │
│  🤔 Agent 追问：             │
│  "端侧模型 confidence 低于   │
│   多少会 fallback 到云端？"  │
│                              │
│  [回答追问] [跳过]           │
└─────────────────────────────┘
```

### 题型 4：场景题

**特点**：最接近真实工作/面试场景，考综合应用能力

**数据结构**：
```json
{
  "type": "scenario",
  "card_id": "p1-arch-003",
  "scenario": "线上监控发现：某用户说'导航去天府广场'，系统走了端侧模型返回 confidence=0.4，然后走了云端 LLM，总延迟达到 6.2 秒。用户投诉响应太慢。",
  "questions": [
    "这个延迟正常吗？哪个环节是瓶颈？",
    "端侧模型 confidence=0.4 说明了什么？为什么没直出？",
    "如果要把这个 case 的延迟降到 1s 以内，有哪些方案？"
  ],
  "reference_analysis": [
    "不正常。正常端侧 ~1s 或云端 ~5s，6.2s 说明走了端侧(失败) + 云端两趟",
    "conf=0.4 < 0.85 阈值 → 端侧放行。可能是'天府广场'这类具体POI名端侧处理不好",
    "方案1: FastRules 加导航短路规则；方案2: 端侧训练数据加 POI 名；方案3: 调低 conf 阈值（有风险）"
  ],
  "related_cards": ["p1-arch-004", "p1-arch-009", "p1-design-009"],
  "difficulty": 4
}
```

**Agent 的作用**（场景题几乎完全依赖 agent）：
1. **生成场景**：从知识卡片 + 项目真实数据中构造贴近实际的场景
2. **多步追问**：场景题天然适合追问链（"还有呢？" "如果X变了会怎样？"）
3. **开放评估**：场景题没有标准答案，agent 评估思路是否合理
4. **引导思考**：用户卡住时，agent 给线索而非答案

**交互**：
```
┌─────────────────────────────┐
│  🎯 场景题                   │
│                              │
│  📋 场景：                    │
│  线上监控发现：某用户说'导航   │
│  去天府广场'，端侧返回        │
│  confidence=0.4，总延迟       │
│  6.2 秒。用户投诉太慢。       │
│                              │
│  ❓ 这个延迟正常吗？哪个环节   │
│     是瓶颈？                  │
│                              │
│  ┌─────────────────────────┐│
│  │ [输入你的分析...]        ││
│  └─────────────────────────┘│
│                              │
│  [提交]                     │
└─────────────────────────────┘

Agent 交互：
┌─────────────────────────────┐
│  Agent: 分析得不错，你提到   │
│  走了两趟推理。那具体说，     │
│  confidence=0.4 说明什么？   │
│  为什么没直出？              │
│                              │
│  你: [输入_______________]   │
│                              │
│  Agent: 对，低于阈值。那要   │
│  把延迟降到 1s 内，你会怎么  │
│  做？(最后一问)              │
│                              │
│  你: [输入_______________]   │
│                              │
│  [结束评估]                  │
└─────────────────────────────┘
```

## 三、题型之间的智能联动

**这是 Agent 的核心价值——不是四种独立的题，而是一个自适应的学习系统：**

```
学习流程：

选择 → ✅ 连续答对 2 次 → 升级到填空
填空 → ✅ 连续答对 2 次 → 升级到问答
问答 → ✅ Agent 评估通过 → 升级到场景
场景 → ✅ 通过 → 🟢 mastered

任何题型 → ❌ 答错 → 降级到低一级题型 + agent 追问
场景 → ❌ → 降回问答，补充薄弱点后再上
```

**降级示例：**
```
场景题答错 → agent 发现是端侧门控概念不清
  → 降级为问答题："端侧 3B 的门控条件有哪些？"
  → 还是答不好 → 降级为填空题："有指代词/多意图/____/____ 不走端侧"
  → 还是不行 → 降级为选择题："以下哪种情况端侧不处理？A.'开空调' B.'最近的那个' C.'导航去机场' D.'查天气'"
```

**自适应出题策略：**

| 卡片状态 | 出题策略 |
|---------|---------|
| 🔴 new | 先出选择题，建立基本认知 |
| 🟡 reviewing (早期) | 填空题 + 选择题交替，巩固记忆 |
| 🟡 reviewing (后期) | 问答题为主，检验理解 |
| 🟢 mastered 前一步 | 场景题验收，确认能应用 |
| 🟢 mastered | 间隔重复，随机出四种题型之一 |

## 四、Agent 题目生成机制

### 4.1 从基础卡片生成选择题

**Agent Prompt（后端用）：**
```
你是一个出题专家。根据以下知识卡片内容，生成一道选择题。

卡片标题：{card_title}
卡片答案：{card_a}
关联知识：{related_cards_content}

出题要求：
1. 从答案中选一个关键知识点出题
2. 4 个选项，1 正确 3 干扰
3. 干扰项必须来自同一知识域的真实数据（不能瞎编）
4. 干扰项要有迷惑性（看起来像对的）
5. 每次选不同的知识点出题（不要总考同一个）

输出 JSON：
{
  "question": "题目文本",
  "options": [
    {"id": "A", "text": "选项A", "correct": false},
    {"id": "B", "text": "选项B", "correct": true},
    {"id": "C", "text": "选项C", "correct": false},
    {"id": "D", "text": "选项D", "correct": false}
  ],
  "explanation": "解析",
  "tested_knowledge": "这道题考的知识点"
}
```

### 4.2 从基础卡片生成填空题

**Agent Prompt：**
```
你是一个出题专家。根据以下知识卡片内容，生成一道填空题。

卡片标题：{card_title}
卡片答案：{card_a}

出题要求：
1. 把关键术语或数据挖空，生成模板
2. 每次挖不同的空（不要总是挖同一个术语）
3. 挖 2-4 个空，不要太多
4. 为每个空提供 2-3 个可接受的替代答案（中文场景需考虑同义词）

输出 JSON：
{
  "template": "三层推理漏斗：L0 ___(~___%) → L1 ___(~___s) → L2 ___(~___s)",
  "blanks": [
    {"id": 1, "answer": "FastRules", "alternatives": ["fast_rules", "前置规则"]},
    {"id": 2, "answer": "40", "alternatives": ["~40"]},
    ...
  ],
  "explanation": "完整答案"
}
```

### 4.3 从基础卡片生成场景题

**Agent Prompt：**
```
你是一个出题专家。根据以下知识卡片内容，生成一道场景分析题。

卡片标题：{card_title}
卡片答案：{card_a}
关联卡片：{related_cards_content}

出题要求：
1. 构造一个贴近真实工作场景的案例（线上问题、设计评审、技术选型等）
2. 场景要涉及这张卡片的核心知识 + 1-2 张关联卡片的知识
3. 给出 2-3 个递进式问题（从现象分析 → 根因定位 → 解决方案）
4. 难度适中，不需要写代码，但需要说清楚思路

输出 JSON：
{
  "scenario": "场景描述",
  "questions": ["问题1", "问题2", "问题3"],
  "reference_analysis": ["参考分析1", "参考分析2", "参考分析3"],
  "related_cards": ["关联卡片ID"],
  "difficulty": 4
}
```

## 六、学习模式

### 模式 1：每日复习（默认入口）

系统根据卡片状态 + 题型等级，自动编排今天的复习题目：

```

  选择题 × 3 (新卡/基础巩固)
  填空题 × 3 (记忆强化)
  问答题 × 4 (理解检验)
  场景题 × 2 (应用验收)
```

出题优先级：
1. 🔴 new 卡片 → 从选择题开始

## 十、设计原则

1. **离线优先**：选择题和填空题预生成缓存到本地，离线可用。问答题和场景题需要 agent，在线时才出。
2. **Agent 是增强不是依赖**：没有 Agent API 时，退化为选择题+填空题（预生成）+ 翻卡问答
3. **数据解耦**：卡片内容归 wiki（我维护导出 JSON），App 只消费。题目可预生成也可 agent 实时生成。
4. **题型渐进**：选择 → 填空 → 问答 → 场景，认知层级递进，不要一上来就场景题
5. **移动优先**：单手操作，选择题按钮大，填空题键盘友好，问答题支持语音输入
6. **预生成 + 实时生成混合**：选择题/填空题可预生成缓存（省 API 调用），问答题/场景题实时生成（更灵活）

## 十一、与本地 Agent 的双向协作

### 11.1 架构概览

```
┌──────────────┐    推送卡片     ┌──────────────┐
│  本地 Agent   │ ────────────→ │   手机 App    │
│  (小洁宝)     │               │  (HTML/PWA)   │
│              │ ←──────────── │              │
│  维护 wiki    │    操作请求     │  学习 + 反馈   │
│  整理知识     │               │  可视化展示    │
└──────┬───────┘               └──────┬───────┘
       │                              │
       │                              │
  wiki/ (SSOT)                 localStorage
  flashcards/                  (学习进度)
  concepts/                    (操作日志)
```

**核心原则**：wiki 是唯一真相源（SSOT）。Agent 写 wiki → 导出 JSON → 推送到 App。App 上的修改请求发回 Agent → Agent 更新 wiki → 再导出推送。

### 11.2 数据流：Agent → App

**场景：Agent 整理了新知识，推送到 App**

```
1. 我在 wiki 上整理了新的复习卡片（或修改了现有卡片）
2. 我运行导出脚本：wiki flashcards → cards.json
3. 我把 cards.json 推送到同步端点
4. App 拉取更新，合并到本地数据
```

**同步 API：**

```
GET /api/sync/cards
Response:
{
  "version": "2026-05-27-v3",       // 数据版本号
  "updated_at": "2026-05-27T14:30:00",
  "cards": [...],                    // 全量卡片（首次）
  "deleted_ids": ["p1-arch-007"],    // 本版本删除的卡片
  "changelog": [                     // 变更记录
    {"id": "p1-arch-003", "action": "updated", "fields": ["a", "eval_keywords"]},
    {"id": "p1-design-016", "action": "added"}
  ]
}
```

App 端处理逻辑：
- 首次：全量加载
- 后续：根据 version 增量更新
- `deleted_ids` → 本地删除（学习记录保留但标记为已删除）
- `updated` → 合并新内容（学习进度不丢失）

### 11.3 数据流：App → Agent

**场景：用户在 App 上操作，请求 Agent 处理**

用户在 App 上不只是被动刷题，还可以主动发起操作：

| 操作 | 说明 | 示例 |
|------|------|------|
| **新增卡片** | 用户输入主题，Agent 自动生成完整卡片 | "帮我加一张讲 RAG 的卡片" |
| **修改卡片** | 用户指出答案有误或需要补充 | "这张卡的答案漏了端侧门控的行程词" |
| **删除卡片** | 用户觉得某张卡不需要了 | "删掉这张，太简单了" |
| **拆分卡片** | 一张卡内容太多，拆成多张 | "这张场景题太复杂了，拆成两张" |
| **合并卡片** | 多张卡内容重复 | "这两张合并一下吧" |
| **生成变体** | 给某张卡生成新的变换问法 | "给这张卡加两个新问法" |
| **补充知识点** | 面试后补充被问到但卡片没有的内容 | "面试被问了端侧训练数据，帮我加到 wiki" |

**操作请求格式：**

```
POST /api/agent/request
{
  "type": "add_card",
  "payload": {
    "topic": "RAG 检索增强生成",
    "deck": "LLM 基础",
    "notes": "面试被问到了，主要讲 retrieve 和 augment 两个阶段"
  },
  "requested_at": "2026-05-27T15:00:00"
}

POST /api/agent/request
{
  "type": "update_card",
  "card_id": "p1-arch-003",
  "payload": {
    "field": "a",
    "action": "append",
    "content": "补充：端侧门控还排除了含行程词的输入"
  }
}

POST /api/agent/request
{
  "type": "delete_card",
  "card_id": "p1-arch-007",
  "reason": "太基础了，不需要复习"
}
```

**Agent 处理流程：**

```
App 发送操作请求
       ↓
本地 Agent（我）收到请求
       ↓
┌─ 新增 → 我整理知识 → 写入 wiki → 导出卡片 → 推回 App
├─ 修改 → 我更新 wiki → 重新导出 → 推回 App
├─ 删除 → 我在 wiki 标记废弃 → 导出时排除 → 通知 App
└─ 其他 → 我处理 → 更新 wiki → 推回 App
```

### 11.5 同步机制设计

**方案：文件同步 + 操作队列**

```
同步目录（本地Agent和App共享）：
  sync/
  ├── cards.json           ← Agent 导出的卡片数据（App 拉取）
  ├── version.json         ← 当前版本号 + 变更日志
  ├── requests.json        ← App 发起的操作请求（Agent 读取处理）
  └── feedback.json        ← App 回流的学习数据（Agent 读取分析）
```

**同步方式（三选一，由部署环境决定）：**

| 方案 | 适用场景 | 实现复杂度 |
|------|---------|-----------|
| **静态文件托管** | 最简单。我把 JSON 放到静态服务器/GitHub Pages，App 每次启动拉取。操作请求通过表单/邮件发给我。 | ⭐ |
| **本地 HTTP 服务** | 我在本地启一个轻量 FastAPI 服务，App 通过局域网 IP 访问。实时双向。 | ⭐⭐ |
| **云数据库** | Firebase/Supabase 做中转。最完善但最复杂。 | ⭐⭐⭐ |

**建议先用「静态文件托管 + 操作请求文件」起步**，跑通流程后再升级。
